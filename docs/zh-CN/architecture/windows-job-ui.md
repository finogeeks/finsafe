# Windows 桌面交互与 Job UI

[English](../../en/architecture/windows-job-ui.md) · [安全原理](README.md) · [Windows 防护说明](../protection/windows-security.md)

让 Agent 运行一个程序，并不需要同时允许它读取剪贴板、修改显示设置或操作其他应用的窗口。Job UI 提供这些桌面交互限制；它与文件权限、网络控制和初始桌面放置分别配置。

**适用范围：** 提供分组 UI 选项的 Windows AppContainer `run`／`self-confine` 启动路径。先用所安装版本的帮助确认选项。桌面应用接入可能提供自己的显式兼容性参数，不能把本页的 CLI 默认值当成每个插件的有效值。本页解释已有公开选项，不新增界面、YAML 字段或运行时编辑入口。

## Job Object 与 UI 限制的关系

Windows Job Object 可以组织进程，并承载生命周期、资源与 UI 限制。Job UI 负责其中的交互边界。进程属于一个 Job，不足以证明某项 UI 限制已经启用；还需核对该 Job 的有效限制。

例如，假设 Agent 只需在测试目录中生成报表。读取系统剪贴板与改动鼠标设置并不是这项任务的必需步骤。Job UI 可以约束相关交互，而文件权限仍允许它在指定目录写入报表。这是场景说明，不是一次测评结果。

## 每类限制分别解决什么问题

| 类别 | 作用 | 不能据此推断 |
| --- | --- | --- |
| 剪贴板读／写 | 分别限制把剪贴板内容读入进程、把内容写到剪贴板 | 允许读取不等于允许写入，也不是按用户点击逐次授权 |
| 外部 USER 句柄 | 限制使用 Job 外进程拥有的 USER 对象，影响相应窗口消息和钩子操作 | 不约束所有文件、进程、管道或其他内核句柄 |
| 全局原子表 | 限制通过该 Windows 共享机制交换信息 | 不等于禁止所有进程间通信 |
| 桌面与会话操作 | 限制对应的桌面创建／切换及会话退出操作 | 不决定进程最初放置在哪个桌面 |
| 系统参数与显示设置 | 限制对应的系统参数和显示配置修改 | 不覆盖所有系统设置、注册表或设备接口 |
| IME 与注入相关限制 | 在支持的 Windows 构建上施加对应限制 | 不保证所有键盘读取、模拟输入或注入途径都已阻断 |

基础行为见 [Microsoft Job UI 说明](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_ui_restrictions)。具体 API 访问还可能受到 AppContainer、对象 ACL 和 Windows 完整性边界影响。

## 默认值与兼容性怎样配合

在上述 CLI 路径中，省略 UI 选项会启用当前 Windows 支持的限制；单独修改一组不会自动放开其他组。初始桌面放置由 `--windows-desktop` 单独控制，省略时为 `isolated`。

完整参数及取值表由 [Windows 系统与桌面防护](../protection/windows-security.md#cli-如何表达-ui-权限)维护。几个容易混淆的选择是：

- `--windows-ui-clipboard read` 移除读限制，写限制仍保留。
- `--windows-ui-isolation desktop` 允许相应 USER 对象与原子表共享，不等于选择 `--windows-desktop inherit`。
- `--windows-desktop inherit` 改变初始桌面共享范围，不会单独清除其他 UI 限制。
- `allow` 只移除该组对应的 Job UI 限制；它不会授予 AppContainer、UIPI 或对象 ACL 仍拒绝的权限。

GUI 应用可能需要窗口共享、复制粘贴或输入法兼容性。接入方应明确传入所需选项，并说明变化后的边界。不能从“界面可用”倒推出所有 UI 防护仍保持 CLI 默认，也不应为解决一种兼容性问题而统一放开所有组。

## Windows 版本会怎样影响结果

FinShield 对不同限制检查主机支持。当前实现以 Windows 构建 `22621` 作为 IME 相关限制的启用门槛，以 `26100` 作为注入相关限制的启用门槛。省略选项时采用主机支持的有效集合；在不支持的主机上显式请求对应的 `deny`，启动会报告错误。

不能比较两个系统的数字掩码就认定保护相同。记录 Windows 构建、明确请求和实际有效限制。系统拒绝应用限制时，应处理原始错误，不将失败写成成功，也不默默改用更弱的限制启动。

范围：一次使用 UI 选项的新 Job 启动。输入：启动选项和 Windows 支持。输出：进程按有效限制运行，或启动错误；不修改已经运行的 Job。

```mermaid
flowchart LR
    A[接收启动选项] --> B[解析各组默认值]
    B --> C[检查 Windows 支持]
    C --> D[应用有效 Job UI 限制]
    D --> E[启动受保护进程]
```

这些选项在创建新沙箱 Job 时生效。已经处于外层受保护运行中的嵌套调用继续使用外层配置；内层传入另一组值不会重配外层 Job，包括内层看似更严格的值。

## 如何验证实际交互

使用可丢弃测试程序、测试窗口和合成剪贴板内容，记录 FinShield、Agent、Windows 构建和启动入口。

| 验证对象 | 检查方法与证据 |
| --- | --- |
| 剪贴板读取 | 从宿主写入独特测试文本，在受保护进程尝试读取，保留 API 结果和实际读到的内容 |
| 剪贴板写入 | 从受保护进程写入另一测试文本，再由独立宿主读取；不要用读测试替代写测试 |
| 外部窗口交互 | 用自建宿主测试窗口，记录具体操作、API 返回和独立可观察效果 |
| 有效限制 | 如当前输出提供 `windows_job_ui_limits`，记录它并与请求选项、Windows 构建对应；字段存在本身不证明每条行为已实测 |
| 应用兼容性 | 在最终 Agent 版本中确认输入、复制粘贴、正常任务和退出，不只验证一个独立测试 EXE |

“没有发生可见变化”还可能来自程序没运行、输入不正确或依赖缺失。缺少拒绝日志也不能证明操作允许；当前文件拒绝记录不等于完整 Job UI 审计。

## 哪些结论仍需单独证明

同桌面的 `GetDC(NULL)` 屏幕读取不由现有 Job UI 掩码阻止。私有初始桌面也不能单独证明所有桌面访问和线程路径均受完整隔离。因此，本页不作“完全防截屏”“所有输入都不可见”或“全部 IPC 被关闭”的承诺。

本页没有重新执行 Windows 原生或已安装 Agent 验收。历史案例只能证明其记录的平台、版本、权限和操作结果。继续阅读[防护边界与验证](../protection/windows-security.md)、[兼容矩阵](../agents/compatibility.md)和[安装验证](../getting-started/install.md#验证授权范围)。
