# 常见问题

## AI safety

### 1. AI safety、AI security、Agent safety 到底有什么区别？

这些术语的用法会随语境变化，本文按关注点区分：AI safety 关注 AI 给人和环境带来的伤害，包括错误判断、有害输出和滥用；AI security 关注对模型、数据及应用的攻击与防护；Agent safety 重点关注系统获得工具和行动能力后，能否按授权执行、限制损失并接受监督。三者相互重叠，例如提示词注入既是攻击，也可能诱发危险行动。

沙箱主要承担执行隔离和权限约束，不能单独解决事实错误、公平性或模型对齐。参见 [NIST 生成式 AI 风险概览](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)与 [OWASP Agent 风险分类](https://genai.owasp.org/top-10-for-agentic-applications-2026/)。

### 2. 模型更聪明、能力更强，是否意味着它更安全？

不能直接推断。更强的模型可能更准确地理解任务，也可能更善于调用工具、编写程序和完成长链任务；同样的权限配置下，这些能力既能提高效率，也可能扩大误操作或滥用的影响。业务能力测试得分与安全性需要分别验证。

评估时应明确模型能做什么、接触哪些资源，以及防护失效后会造成什么后果。模型升级后也要复核这些条件，不能把旧版测评直接当作新版保证。参见 [OpenAI 对能力风险与防护的说明](https://openai.com/index/updating-our-preparedness-framework/)。

### 3. 模型经过安全训练，为什么还需要运行时保护？

安全训练影响模型怎样选择行动，运行时保护约束行动实际能到达哪些资源。训练无法预先覆盖每份外部内容、每个工具实现和每种部署配置；即使模型误判或写错代码，权限边界仍应限制受保护进程的访问。

例如，告诉 Agent 不要修改私人目录，与让执行进程没有修改权限，是不同层面的措施。应把模型训练、工具授权、文件与网络隔离以及结果检查结合起来，而不把任何一层当成完整保证。参见 [Anthropic 的操作系统级沙箱设计](https://www.anthropic.com/research/claude-code-sandboxing)。

### 4. 提示词注入、越狱和普通的任务误解，有什么区别？

提示词注入是输入中的指令影响模型，使其偏离应用原定行为；它可以来自直接输入，也可以藏在网页、邮件或工具结果中。越狱重点是绕过模型的安全限制，两者可能重叠。普通任务误解则可能没有攻击者：例如用户要求清理临时文件，Agent 却误删仍需保留的资料。

区分原因有助于改进防护，但实际损失不能只按是否存在攻击者判断。面对三种原因，都需要核对被调用的工具、权限和最终效果。参见 [OWASP 的注入与越狱说明](https://genai.owasp.org/llm2026/llm012026-prompt-injection/)。

### 5. 能否彻底防住提示词注入？如果防不住，应该怎样限制后果？

目前不应作出“所有输入都能识别并阻止”的保证。检测和训练可以降低风险，系统设计还需要考虑模型被诱导成功的情况：减少可读数据、缩小工具权限和网络目的地、隔离不可信执行，并对高影响操作作独立检查。

例如，读取公开网页的 Agent 不必同时持有云管理密钥。限制损失还要检查沙箱外的 API 和业务工具；沙箱不会自动拦住获准账户在获准服务上的错误操作。参见 [OpenAI 的分层防护说明](https://openai.com/safety/prompt-injections/)与 [OWASP 防护指南](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。

### 6. 谁来判断 AI 是否安全：模型提供商、应用开发者、用户，还是独立测评机构？

需要分工，不能由单方的一句“安全”代替完整判断。模型提供商评估模型能力和已知风险；应用开发者验证工具、授权及数据流；部署方确定适用场景和可接受风险；用户表达任务意图并审查关键结果。独立评估可提供额外证据，但结论仍受测试范围限制。

评估应贯穿生命周期，记录版本、环境、方法和残余风险，并尽量把开发与验证职责分开。一次测评通过不等于覆盖所有业务，也不自动构成认证。参见 [NIST AI RMF 的参与者与评估职责](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf)。

## Agent safety

### 7. 为什么一个“只会聊天”的模型，接上工具以后，安全问题就变了？

因为回答开始产生外部效果。错误建议原本需要人再执行；接上文件、终端、邮件或业务 API 后，模型可能直接改文件、发消息、执行程序和消耗预算。即使工具本身正常、调用也没有越权，错误的对象、参数或调用顺序仍可能造成损失。

所以需要同时检查模型判断和工具实际能做什么，把读、写、删除、发送等能力按任务拆开授权。一个没有恶意、只是误解任务的 Agent，也需要这些限制。参见 [OWASP 工具滥用风险](https://genai.owasp.org/agentic-applications-2026/asi02-tool-misuse-and-exploitation/)。

### 8. 用户授权一个任务，是否等于授权完成任务所能用到的一切操作？

不等于。任务描述表达目标，权限应限定可访问的资源和可执行的操作。例如“汇总账单”不自动包含删除账单、读取其他客户资料或发送邮件的许可；Agent 认为某项操作“有帮助”，也不能代替授权。

可以把要求落实为只读指定目录、限制查询对象、限定执行时段等规则。发现任务需要额外资源时，再由有权决定的人或策略流程评估。这个做法遵循[最小权限原则](https://csrc.nist.gov/glossary/term/least_privilege)：完成指定职责所需的权限，不应被扩展成用户拥有的全部权限。

### 9. Agent 应该继承用户的全部权限，还是拥有单独、受限的执行身份？

通常应采用可识别、受限的执行身份，并按任务或会话授予必要权限。否则，一个本来只需整理文件的进程，可能同时获得用户的其他文件访问权、登录令牌或管理权限，事故范围也随之扩大。

本机进程身份和远程服务身份需要分别控制：本地进程受限，不代表其持有的 API 密钥权限也已缩小。应在服务端限制令牌的资源、操作和有效期，并保留谁代表谁执行的记录。参见 [OWASP 身份与权限滥用](https://genai.owasp.org/agentic-applications-2026/asi03-identity-and-privilege-abuse/)。

### 10. Agent 读到网页、邮件、代码仓库里的恶意指令，会不会替攻击者做事？

有可能。外部内容本应是任务资料，攻击者却可能在其中夹带指令，诱导 Agent 改变目标、泄露资料或调用工具。这类间接提示词注入不要求攻击者拥有用户的账号；能影响 Agent 将读取的内容，就可能形成入口。

应保留资料来源及信任级别，限制接触不可信内容的流程所能调用的工具，并在执行层限制资源与外发范围。输入过滤、模型训练和人工确认可以配合使用，但不能据此承诺所有注入都会被识别。参见 [OpenAI 提示词注入说明](https://openai.com/safety/prompt-injections/)。

### 11. 每次操作都弹确认框，真的能保护用户吗？哪些边界不能靠一次确认放开？

确认有用，但效果取决于用户能否看懂要操作的对象、影响范围及后果。只显示命令名或 Agent 自己生成的理由，可能使用户在不了解风险时批准；频繁确认也容易让人习惯性点击。

确认应针对具体操作，并展示可核对的预览。组织预先禁止的数据外发、受保护凭据访问等，应由相应权限和管理规则约束，不能把普通的“继续”解释为有权取消这些规则。参见 [OWASP 人与 Agent 信任风险](https://genai.owasp.org/agentic-applications-2026/asi09-human-agent-trust-exploitation/)。

### 12. Agent 换工具、写脚本、启动子进程后，原来的限制还有效吗？

取决于限制的执行位置和覆盖范围。若只在某个文件工具检查路径，Agent 改用终端访问就可能走另一条通道；操作系统级限制可以约束受保护进程及其子进程，但前提是它们确实在该边界内。

远程 MCP、浏览器服务或在外部运行的工具还需要各自的权限控制。应列出实际执行路径，用同一测试资源分别验证文件工具、脚本和子进程，而不是只验证一次调用。参见 [Anthropic 对命令、脚本及子进程隔离的说明](https://www.anthropic.com/research/claude-code-sandboxing)。

### 13. MCP、插件、Skills 和第三方依赖，会不会成为新的攻击入口？

会，但它们带来的信任不同：工具描述和 Skill 文本可能影响 Agent 的判断，插件或依赖代码则可能直接执行；远程服务还可能接收发送给它的数据。安装成功、名称熟悉或符合协议，不等于来源和行为都可信。

应核实来源、版本和更新渠道，评估其代码权限与数据去向，并用有限权限验证实际行为。版本固定与签名有助于追溯来源，不能单独证明组件没有恶意。参见 [OWASP Agent 供应链风险](https://genai.owasp.org/agentic-applications-2026/asi04-agentic-supply-chain-vulnerabilities/)。

### 14. 多个 Agent 相互委托时，权限会不会被逐步放大？

可能，尤其是共享高权限令牌，或高权限 Agent 不核验请求便替低权限 Agent 操作时。防护不应因“内部 Agent 发来的请求”而跳过检查；每次委托仍需明确任务范围、当前执行者和目标资源。

委托链应限制下游可获得的权限，并记录发起者、执行者和授权范围。身份标准中的委托记录可以帮助表达这条链，但记录本身不等于正确执行了访问控制。参见 [IETF OAuth 令牌交换与委托语义](https://www.rfc-editor.org/rfc/rfc8693.html)。

### 15. Agent 出错或失控后，能否及时停止、查清影响，以及恢复损失？

这是三个需要分别准备和验证的能力。停止需要能够终止后续执行、撤销相关凭据并处理已派发任务；调查需要保存身份、授权、工具调用和结果等记录；恢复依赖备份、版本历史或业务系统支持的补偿操作。

停止本机进程不一定取消已提交的远程任务，也不会收回已发送的数据、撤销转账或自动恢复文件。应在部署前演练这些流程，明确哪些后果不可逆。参见 [NIST 事件响应与恢复建议](https://csrc.nist.gov/pubs/sp/800/61/r3/final)。

## Sandbox

### 16. 沙箱保护的到底是什么：宿主机、数据、其他应用，还是执行环境自身？

取决于威胁模型和实现。常见目标是限制不可信程序对宿主资源、数据及其他进程的影响；有的环境还隔离不同任务或租户。Windows AppContainer 就分别约束设备、文件、网络、进程和窗口访问，但实际授权决定开放哪些资源，不能从“用了沙箱”推导全部受保护。[Microsoft 隔离说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)

评估时应列明保护对象、执行范围、共享资源和例外。沙箱不能自动判断业务行为是否正确，也不等于保护其中的程序免受宿主管理员控制。

### 17. 沙箱、容器、虚拟机、命令审批和工具权限控制，有什么区别？

它们位于不同层次，可以组合使用。“沙箱”描述限制程序活动的环境或机制，不是一种固定的底层技术。

| 方式 | 主要控制什么 | 需要注意 |
| --- | --- | --- |
| 沙箱 | 执行过程能接触的资源及操作 | 实际边界取决于实现、策略和覆盖路径 |
| 容器 | 进程、文件系统及网络等运行视图 | 常见 Linux 容器共享内核；权限、挂载和宿主接口仍需控制 |
| 虚拟机 | 使用独立客户操作系统的执行环境 | 共享目录、设备和管理接口仍会开放访问路径 |
| 命令审批 | 某次命令是否允许开始执行 | 批准一条命令不等于约束其全部后续行为 |
| 工具权限控制 | 哪些工具和参数可被调用 | 已获准工具的底层权限与远端服务权限还需单独限制 |

容器与虚拟机的架构区别见 [Docker 官方介绍](https://docs.docker.com/learn/content/what-is-a-container/)。选型应比较实际配置与威胁模型，而非只比较名称。

### 18. 沙箱限制的是某个工具，还是 Agent 的整个执行链？哪些操作在边界之外？

两种设计都存在，必须逐条追踪执行路径。只隔离 shell 命令，不能据此认定文件工具、浏览器、远程 MCP 和云端 API 都受同样限制；子进程是否继承约束，也要按实际实现验证。

例如 Anthropic 的 Managed Agents 文档明确区分沙箱中的命令／文件工具、服务端网络工具和应用自己的自定义工具。应画出“模型→工具→进程或服务→资源”的路径，为每段注明控制者；本机进程限制不能代替远端服务的身份与权限检查。[执行边界示例](https://platform.claude.com/docs/en/managed-agents/secure-deployment-risks)

### 19. 文件只读、网络白名单、PII 检测，各自解决什么问题？为什么不能互相替代？

文件只读限制修改，不阻止读取；网络白名单限制能连接的目标，不保证发往获准目标的内容安全；PII 检测识别所覆盖内容中的特定敏感类别，不等于检查所有文件、格式和出站通道。

例如 Agent 可以读取只读文件，再把内容发送给获准模型。要限制这种外发，还需核对内容检查覆盖及命中处理：告警可以允许发送，阻断才拒绝该请求，脱敏则需要有效改写。应分别验证“能读什么、能连哪里、实际发了什么”。[网络与 PII 范围](../protection/network-pii.md)

### 20. 沙箱里的程序能否读取和使用用户的密钥、登录状态及云服务凭据？

如果密钥通过可读文件、环境变量、工具结果或登录资料暴露给程序，就不能因为它在沙箱里运行而认定密钥安全。应同时检查凭据能否被读取，以及程序能否借助它调用服务。

一种设计是将凭据保存在执行环境之外，由代理向指定请求注入；这能减少原文暴露，但程序仍可能执行凭据允许的操作。还需在签发服务限制账号、资源和操作权限，并具备撤销能力；“看不到密钥”不等于“无法滥用授权”。[凭据隔离与权限说明](https://platform.claude.com/docs/en/managed-agents/secure-deployment#keep-credentials-in-vaults)

### 21. 没有发生沙箱逃逸，Agent 是否仍可能删错文件、泄露数据或滥用业务权限？

会。沙箱逃逸指突破隔离边界；在已有权限内做错事，并不需要逃逸。例如误删可写工作区、把获准读取的资料发到获准服务，或者通过高权限业务工具删除订单，都可能发生在技术边界以内。

因此还要缩小工具功能、数据范围与远端账号权限，并对高影响操作作专门控制。OWASP 将过多功能、权限和自主性列为“过度代理能力”的根因；这说明“进程仍在沙箱中”不能作为业务安全的充分证据。[OWASP 风险说明](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

### 22. 安全规则由谁修改？Agent 能否通过申请权限、换工具或修改配置绕开限制？

规则应由有权限的用户或管理员维护。Agent 可以说明受阻原因、申请具体资源，但申请本身不应等于授权。需要区分只影响一次操作的审批、允许沙箱外执行的例外，以及修改长期策略；这些改变会产生不同边界。

检查重点是策略和控制接口是否对受保护进程可写、所有执行路径是否落实限制，以及保护不可用时会拒绝还是转为普通运行。厂商也提供不同配置：Anthropic 的企业指南区分默认例外和管理员强制沙箱设置，不能一概断言原生沙箱都能或都不能绕开。[企业策略示例](https://claude.com/resources/articles/enterprise-guide-to-securing-coding-agents)

### 23. 隔离越严格，是不是越安全？怎样同时验证安全性、任务可用性和性能？

对某类资源收紧权限，通常会缩小相应风险，但整体安全还取决于共享接口、凭据、实现缺陷和运维。不能用“多禁几个操作”证明方案更好，也不能先假定某种隔离必然更快或更慢。

建议固定 Agent、模型、任务、主机和配置，分别测越界效果是否阻止、正常任务是否完成，以及启动时间、任务耗时和资源开销；记录失败原因与例外，升级后重测。这是评估建议，不是本文已测出的性能结论。NIST 也要求说明测试的适用条件，避免从少量案例外推能力。[NIST 测评指导](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

### 24. 怎样证明沙箱有效：出现拒绝提示就算，还是要检查最终实际效果？

要检查实际效果，并确认有效操作确实被尝试。程序没运行、依赖缺失、路径写错或模型口头拒绝，都不能单独证明隔离成功。测试应同时包含获准操作和越界操作，核对文件、设备、进程或接收端的真实状态。

保留版本、策略、启动入口、审批过程、工具返回和外部观察。初始拒绝、批准后的结果与最终损害分别记录；某个效果未发生，也不自动证明由哪个系统接口拦截。公开记录还应说明未测范围和判定局限。[测评方法与证据要求](whitepaper.md#附录b测评方法与统计范围)

## FinShield

### 25. Agent 已有原生沙箱，为什么还需要 FinShield？具体补齐了什么缺口？

当原生防护没有覆盖你的资源范围、接入形态或管理要求时，才有增加独立防护的理由。FinShield 面向现有 Agent 的受控接入，把用户设定的资源边界交给执行环境落实，并在支持的配置中提供运行记录。我们的主张是：完成任务遇到困难，不应自动成为扩大权限的理由。

一个具体例子是[历史测评资料](whitepaper.md#32各类风险的覆盖差异)的 2026 年 11 月 25 日 Windows 统计快照：Codex CLI 原生组数据类为 8/8，系统类为 0/13，FinShield 对照配置系统类为 13/13。这说明在那组版本与配置下，文件防护有效仍可能存在其他操作缺口；不能据此断言当前或所有原生沙箱都存在相同问题。

原生沙箱也在使用系统级约束，不能概括为只靠提示词或确认框，见 [Anthropic 的设计说明](https://www.anthropic.com/research/claude-code-sandboxing)。FinShield 是否补齐缺口，要结合[兼容矩阵](../agents/compatibility.md)与[防护说明](../protection/README.md)，用同一任务分别验证获准操作和越界操作。

### 26. 操作系统已经有 AppContainer、Seatbelt 等机制，FinShield 增加了什么产品价值？

操作系统提供隔离基础，产品还要解决实际 Agent 怎样进入保护、需要开放哪些资源、授权后怎样启动，以及升级后怎样确认仍然有效。FinShield 把这些环节组织成插件、桌面或 CLI 接入流程，减少用户自行适配和维护的工作；不同入口的交付范围分别说明。

例如 AppContainer 本身已有文件、进程和窗口隔离能力，见 [Microsoft 说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)。FinShield 复用这些能力，不把平台机制宣传为独有发明。当前机制与记录范围见[安全原理目录](../architecture/README.md)和[Inspector 说明](../architecture/inspector.md)，具体接入见[安装指南](../getting-started/install.md)。

### 27. 为什么选择在现有电脑上约束 Agent，而不是把整个任务搬进虚拟机或远程环境？

因为有些任务需要使用已有的本机文件、工具和应用。FinShield 的接入路线允许用户保留受支持的工具链，同时限制受保护执行进程的资源访问；不必先把整个工作环境迁走。需要原有桌面界面的接入，也要区分普通界面与受保护的执行 Host。

如果任务可以完整迁入独立环境，或要求独立客户机内核等隔离条件，应评估相应的虚拟机或远程方案。本机进程隔离不等价于虚拟机，远程运行也不自动解决共享目录、凭据和业务权限问题。选型看[实际接入范围](../agents/compatibility.md)和工作要求；本站测评不能证明性能优于这些方案。

### 28. FinShield 与原生沙箱是替代、补充，还是可以组合？组合后由谁执行哪些规则？

要按具体接入方式判断。Agent 自身可能管理工具调用和审批，FinShield 则约束接入的执行进程及其受控路径，远程服务仍执行自己的账号权限。只有同一次操作确实经过这些控制点，才谈得上组合防护；经过多层控制不代表每层覆盖所有工具。

不能默认把对照测评理解为“原生开关不变，再叠加 FinShield”。[历史测评的配置与审批说明](whitepaper.md#b2审批与配置)明确要求结合各案例理解两组配置。实际部署应记录谁启动进程、谁授权文件与网络、谁限制外部工具，再按对应 [Agent 指南](../agents/README.md)验证，避免由一层的“已保护”状态代替整体检查。

这些都应该成为比较维度，但只能按公开交付和证据逐项回答，不能仅凭功能名称判定领先。

| 保护范围 | 文件、设备隐私、桌面和系统操作；网络内容检查另有条件 | [防护说明](../protection/README.md) |

### 30. 什么情况下值得使用 FinShield？什么情况下现有方案已经足够？

当受支持的 Agent 需要使用现有电脑上的资料和工具，而你又需要限制其他文件、设备或系统操作时，值得用实际任务评估 FinShield。使用多款 Agent、需要单独核对执行权限和受支持运行记录的团队，也可以检查它是否减少了接入与管理工作。

如果现有环境已经满足你的资源边界和部署要求，就没有必要仅为多一层沙箱而增加复杂度。选型时同时验证正常任务、越界操作、所需记录及运行成本；不要只比较拒绝次数。先看[兼容矩阵](../agents/compatibility.md)，再做[授权范围验证](../getting-started/install.md#验证授权范围)。

### 31. FinShield 明确不能解决哪些问题？哪些能力并非默认开启？

FinShield 的执行边界不保证模型回答正确、消除提示词注入、判断所有业务操作是否合理，也不提供文件备份或撤销。获准可写的位置仍可能被修改或删除；普通桌面进程、未接入路径及远程服务行为需要分别检查。

公开 DSH／OpenCode Windows 插件默认使用 `network.mode: host`，不因此启用网站限制、HTTPS 内容检查或 PII 脱敏；文件基线为 `read_write`，不是默认禁止所有工作区外访问，也没有通用 `.env` 文件名拒绝规则。PII 检测命中也不必然阻断或脱敏。详见[默认防护](../protection/defaults.md)与[网络／PII 范围](../protection/network-pii.md)。

### 32. 如果其他 Agent 厂商继续加强原生沙箱，FinShield 长期存在的价值是什么？

长期价值需要持续证明：能否让用户在受支持的不同 Agent 上落实资源要求，降低接入与维护成本，并提供可复查的保护效果和运行记录。独立防护的职责是围绕用户愿意交出的权限作设计；这是一项产品方向，不代表独立产品天然更安全。

我们应随 Agent、操作系统和攻击方式的变化更新适配与证据。如果某款原生方案已经完整满足用户需求，应承认它可以足够。FinShield 的价值来自持续补齐实际缺口，而不依赖“其他沙箱永远做不好”的假设。当前依据见[兼容范围](../agents/compatibility.md)、[公开测评](whitepaper.md)及[产品介绍](../overview/README.md)。
